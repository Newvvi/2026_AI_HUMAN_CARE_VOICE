# 11. 단어 인식 갈래: 직접 녹음 평가와 파이4 실측 (2026-11-07 ~ 11-08)

> 소리 분류 모델(CNN, YAMNet)을 **직접 녹음한 일상 소리**로 시험했더니 쓸 수 없다는 것이 드러났고, 그래서 **말소리를 글자로 바꿔 위급 단어를 찾는 방식**으로 바꿨습니다. 이 문서는 그 과정과 파이4 실측을 기록합니다.
> 숫자는 모두 **음성 팀 한 명이 만든 녹음**(한 집, 기기 두 대, 같은 목소리 위주) 기준이라 실제보다 낙관적일 수 있습니다. 확인하지 못한 것은 `(확인 필요)`, 측정이 아닌 값은 `(추정)`으로 표시했습니다.

## 2. 왜 방향을 바꿨나

11/05까지의 소리 분류 모델은 AI Hub 데이터 안에서는 좋았습니다 (재현율 0.87~0.96). 그러나 **직접 녹음한 일상 소리**에 적용하자 달라졌습니다 (§4). 재현율을 90% 근처로 올리려면 오경보가 시간당 수십~수백 회였고, 오경보를 시간당 몇 회로 줄이면 재현율이 10~25%로 떨어졌습니다.
원인으로 보는 것: YAMNet 임베딩은 "큰 소리로 외치는 말"과 "평범한 말소리"는 구분하지만 **단어 내용은 거의 듣지 못합니다**. 같은 기기·같은 목소리의 평범한 "도와주세요"는 소리 모양만 보면 일상 대화와 같습니다. 그래서 단어를 직접 듣는 방식을 시험했습니다.

## 4. 소리 분류 모델의 결과 (YAMNet 임베딩 + MLP)

### 4-1. AI Hub 안의 오경보와 일상 소리의 오경보 (같은 설정)

| 모델 | AI Hub 정상 소리 1.11시간 오경보 | 시험용 일상 소리 39분(0.65시간) 오경보 |
|---|---|---|
| 03 (N=2·0.95) | 시간당 7.2회 | **시간당 약 628회** (411번) |
| 03b (N=2·0.9) | 시간당 1.8회 | **시간당 약 407회** (266번) |
| 04, 학습용 녹음 40분 추가 (N=2·0.95) | - | 시간당 약 12회 (8번), AI Hub 위급 재현율 0.822 |

오경보를 AI Hub 정상 소리로만 재면 수백 배 낮게 나옵니다. 일상 말소리(대화, 통화, TV)가 정상 데이터에 거의 없었기 때문입니다.

### 4-2. 같은 모델을 3시간 연속(C, 학습에 쓰지 않은 기기)으로 시험

N은 연속 프레임 수, 쉬는 시간은 5초. 재현율은 "도와주세요" 34번 중 앞뒤 1초 안에 알림이 울린 비율.

| 모델·설정 | 재현율 | C 오경보 (시간당) |
|---|---|---|
| 03b N=1·0.5 | 34/34 (100%) | 772회 (257) |
| 03b N=2·0.95 | 29/34 (85%) | 277회 (92) |
| 04 N=1·0.5 | 26/34 (76%) | 362회 (121) |
| 04 N=2·0.95 | 8/34 (24%) | 23회 (7.7) |
| 05 N=1·0.5 | 14/34 (41%) | 230회 (77) |
| 05 N=2·0.9 | 3/34 (9%) | 8회 (2.7) |

- **어느 설정에서도 "재현율 90% + 오경보 시간당 1회"가 되지 않았습니다.** 곡선을 따라 오경보를 줄이면 재현율이 같이 무너집니다.
- **학습에 쓴 소리에서의 오경보는 낙관적입니다.** 05(시험용까지 학습)의 N=2·0.5는 학습에 쓴 녹음에서 시간당 1.5회였는데, 다른 기기의 C에서는 19회였습니다 (약 13배).
- 기기 쏠림은 아니었습니다. 03b는 두 기기 모두 17/17, 05는 6/17과 8/17입니다.
- AI Hub 시험 클립을 종류별로 보면 05 N=2·0.9가 C 오경보 시간당 2.7회에서 신음·비명 85%, 쿵·넘어짐 89%, 말 74%입니다. 다만 이 클립들은 말에 효과음이 섞인 연기라 순수한 신음·쿵 소리를 잡는다고 단정하지 않습니다. 그리고 시간당 2.7회는 하루 약 65회라서 **소리 모델 단독으로 폰 알림을 보내지 않고**, 영상이 같이 잡힐 때만 쓰는 보조 신호로 남깁니다 ([02 D25](02_DECISIONS.md)).

## 5. 말소리를 글자로 바꾸는 방식

### 5-1. Whisper 크기 비교 (코랩, HF fp16, GPU)

응급 34번, C 3시간, 다른 녹음 87분. 규칙은 §5-2의 엄격/느슨.

| 크기 | 재현율 (엄격 / 느슨) | C 오경보 | 다른 녹음 오경보 | 구간당 시간 (GPU / 코랩 CPU) |
|---|---|---|---|---|
| tiny | 30/34 / 32/34 | 1회 | 0 | 0.08초 / 2.4초 |
| base | 27/34 / 29/34 | 1회 | 0 | 0.12초 / 4.9초 |
| small | 31/34 / 32/34 | 1회 | 0 | 0.33초 / 14초 |

- **tiny가 base보다 잘 알아들었고** small과 거의 같았습니다. 놓친 것은 주로 M11 Air 녹음이었습니다 (기기에 따라 인식이 다름).
- C의 오경보 1회는 크기마다 다른 시각의 일상 말("좀 도와주세요" 같은 부탁, "도와줘!")이었습니다. 글자만으로는 위급과 구분되지 않는 표현입니다.

### 5-2. 단어 규칙 (엄격/느슨 + 보강)

- 처음 규칙은 부분 일치라서 **"연구해서" 속의 "구해"**, **"도와주신 거는 감사한데…"의 "도와주"** 를 위급으로 잡았습니다 ([09 #27](09_CORRECTIONS_AND_LESSONS.md)). **단어 앞이 띄어쓰기·문장 시작일 때만, 그리고 "도와주세요/도와줘/살려줘/구해줘/사람 살려/119 불러" 같은 완성된 표현만** 인정하도록 고쳤습니다 ("도와줘서", "도와주셔서"는 제외). 잘린 "도와주세"도 인정합니다.
- 새 문장 시험에서 tiny는 "119"를 "엘리고/빌리고/인누고"처럼 매번 다르게 받아 적고 "불러주세요"만 정확했습니다. 그래서 규칙에 **"불러주세요"** 와 **문장 끝의 "살려"** 를 추가했습니다 (`code/voice_pi/rules_eval.py`).

| 규칙 | tiny | base | small |
|---|---|---|---|
| 기본 (119 / 사람 살려 / 살려주세요) | 0 / 7 / 6 | 0 / 10 / 10 | 4 / 8 / 11 |
| 보강 (불러주세요 + 문장 끝 살려) | 12 / 9 / 6 | 10 / 11 / 10 | 13 / 11 / 11 |

- 오경보: 보강 규칙으로 C 244구간, 다른 녹음 740구간에서 새로 걸린 말은 0개였습니다. **"택시 불러주세요", "분위기를 살려" 같은 일상 표현과는 겹칠 수 있으니** 실제 집에서 확인이 필요합니다.
- 합계(보강 규칙, 새 문장 39번): tiny 27 (69%), base 31 (79%), small 35 (90%).

### 5-3. 반복 규칙과 음량 게이트 (tiny, 코랩)

- 직전 인식에서 30초 안에 또 인식되면 "긴급", 아니면 "주의"로 세었을 때: 응급 녹음 주의 2 / 긴급 28, C 주의 1 / 긴급 0, 다른 녹음 0 / 0.
- 음량 게이트(구간의 가장 큰 음량이 기준보다 작으면 Whisper에 보내지 않음): 응급 발화는 중앙 -19dBFS, C의 말소리 구간은 중앙 -34dBFS. 기준 -30dBFS에서 구간이 시간당 260개 → 68개(74% 감소)로 줄고 재현율은 같았습니다. -25dBFS는 시간당 13개, 재현율 28/34. **같은 dBFS 기준이 기기마다 다르게 작동**해서 reSpeaker에서 다시 맞춰야 합니다.

## 6. 파이4 실측 (faster-whisper, int8, 스레드 2~4)

### 6-1. 속도가 튀던 원인

처음 구간 24개(합계 117초)를 재니 tiny 구간당 평균 9.6초(최대 50초), 실시간의 1.98배였습니다. **재시도(온도를 올려 다시 인식)와 되풀이 출력** 때문이었고, 온도 0·출력 32토큰으로 제한하자 평균 1.94초(최대 2.42초, 실시간의 0.40배, 스레드 4)로 줄었습니다. 스레드 2에서는 2.60초. **구간 길이와 상관없이 구간당 시간이 거의 일정**합니다(2초짜리도 10초짜리도 1.8~2.4초). Whisper가 입력을 30초로 채워 처리하기 때문입니다.

### 6-2. 설정별 시험

**(가) 구간 24개(응급 12 + 일반 12, 합계 117초) 표본, 파이4 스레드 4**

| 설정 | 응급 구간 인식 / 일반 구간 오인식 | 구간당 평균 (최대) | 결론 |
|---|---|---|---|
| 재시도·출력 길이 제한 없음 | 9/12 / 0/12 | 9.6초 (50초) | 시간이 튐 → 제한 |
| 온도 0, 출력 32토큰 | 7/12 / 0/12 | 1.94초 (2.42초) | **채택** |
| + 내장 VAD | 6/12 / 0/12 | 2.03초 (2.54초) | 느리고 재현율 하락 → 기각 |

**(나) 응급 녹음 e1(기기 1)·e2(기기 2) 각 17번, 3시간 C, 다른 녹음 87분 (스레드 2)**

| 설정 | e1 | e2 | 오경보 (C / 다른 녹음) | 결론 |
|---|---|---|---|---|
| 소리 크기 정규화 (끔 / 0.7 / 0.95) | 17 / 17 / 17 | 10 / 8 / 11 | | 효과 없음 → 기각 |
| **탐색 폭 5** | 17 | 15 | 0 / 0 (다른 녹음은 첫 인식 기준) | **채택** (구간당 +0.1초) |
| 미리 알려 준 단어 | 17 | 17 | **C 48회** | **오경보 폭증 → 기각** |
| 하이브리드 (재시도에만 단어, 폭 5) | 17 | 17 | 0 / **3회** | 다른 녹음에서 오경보 → 기각 |
| **재시도 small (단어 없음) + 규칙 보강** | 17 | 17 | **0 / 0** | **채택** (평균 2.7초) |

- **미리 알려 준 단어**(`--prompt "도와주세요. 살려주세요."`)는 응급 재현율을 17/17로 올렸지만 3시간에서 같은 단어가 48번(시간당 16회, 연속으로 몰려서) 만들어졌습니다. 정상 말과 잡음에서도 그 단어를 억지로 써낸 것입니다. **응급 재현율만 보고 확정했다면 놓쳤을 문제**입니다 ([09 #22](09_CORRECTIONS_AND_LESSONS.md)).
- 온도 0.4의 무작위 재시도는 같은 실패 구간에서 건진 수가 5, 2, 3, 0개로 들쭉날쭉해서 결정적인 방법(폭 5, small 재시도)으로 바꿨습니다.
- 재시도 small은 "첫 인식에 주세/와줘/도와/살려/구해/119/일일구 조각이 있지만 단어는 없는" 구간에만 씁니다 (다른 녹음 740구간 중 5개, C 244구간 중 0개). 살려주세요 13번 중 재시도 6번에 4개를 건졌습니다.

|---|---|---|---|
| tiny | 2.7초 | 27/39 (69%) | 주 모델 |
| base | 5.5초 | 31/39 (79%) | 5초 간격 반복 호출이면 아슬아슬 |

### 6-4. 열 (방열판 없음)

- 유휴 63.7℃에서 시작. 3시간 시험(구간 553개, -32dBFS): 최고 83.7℃, `get_throttled`가 `0xe0008`(지금 온도 소프트제한). -28dBFS·스레드 2·모든 구간 재시도: 최고 79.8℃. 최종 검증 배치(약 40분 연속): 최고 82.7℃, 온도 소프트제한.
- `get_throttled` 읽는 법: 하위 비트(0x1, 0x2, 0x4, 0x8)는 **지금**의 저전압·클럭 제한·스로틀링·온도 소프트제한, 상위 비트(0x10000, 0x20000, 0x40000, 0x80000)는 **부팅 후 한 번이라도 발생**한 기록입니다. `0x80000`만 보이면 "과거에 온도 제한이 걸린 적 있다"는 뜻이고 지금 걸려 있다는 뜻이 아닙니다 ([09 #25](09_CORRECTIONS_AND_LESSONS.md)).
- 방열판을 붙이거나 부팅 직후(표시를 지운 뒤)에 시험하면 더 정확합니다. 최종 파이5는 방열 케이스를 사용합니다.

## 9. 한계와 미해결

1. **"도와주세요" 외 문장은 약 70~90%.** 어르신 목소리, 다급하거나 흐릿한 발음, 먼 거리, TV 속 대사는 시험하지 못했습니다.
2. **일상 표현과 겹치는 단어**: "좀 도와주세요", "택시 불러주세요", "분위기를 살려" 같은 말. 글자만으로는 구분할 수 없어서 반복 규칙, 영상 결합, 음량 게이트로 보완합니다.
3. **기기·마이크 차이**: 기기 2(M11 Air)에서 인식이 더 나빴습니다. reSpeaker에서 기준 음량과 재현율을 다시 재야 합니다.
4. **재시도(small)가 처리를 막음**: v0.2까지는 구간을 순서대로 처리해서 재시도 하나(약 20초)가 뒤따르는 구간을 늦췄습니다. v0.3은 재시도를 별도 작업 줄로 분리하고 대기 줄이 가득 차면 건너뛰도록 고쳤고, 파이에서 실시간 속도로 확인했습니다: 일반 발화는 약 3.1초, 재시도로 건지는 발화는 약 24초에 나오고 첫 인식은 막히지 않았습니다 ([§7-1](#7-1-서비스-v03-파이-확인-2026-11-08-파일을-소리처럼-흘려-보낸-시험-실제-마이크-아님)). 마이크 입력에서는 아직 확인하지 못했습니다.
5. **마이크 모드 미시험**: `--mic`와 MQTT 전송은 가짜 모델로 흐름만 확인했고 실제 장비에서는 아직 시험하지 못했습니다.
6. **열**: 방열판 없는 파이4에서 온도 제한이 걸림.
7. 소리 모델은 보조 신호로만 남음 (단독 알림 금지). 비명·신음·쿵 소리의 별도 경로는 아직 없음.
8. 평가는 한 사람이 한 집에서 만든 녹음이라 일반화는 보장되지 않음.
9. **오경보 0회는 그 녹음에 대해 약간 낙관적입니다.** 단어 규칙의 결함 두 가지("연구해서", "도와주신")와 재시도 조건을 같은 녹음(C, 다른 녹음)에서 발견해 고친 뒤의 값이라, 처음 보는 집·사람·TV에서의 오경보는 따로 확인해야 합니다.
