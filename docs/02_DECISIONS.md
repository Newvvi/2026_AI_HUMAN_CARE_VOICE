# 02. 판단 기준과 의사결정 기록

> 이 문서는 "무엇을 선택했는가"보다 **"왜 그렇게 판단했는가"**를 남기기 위한 것입니다.
> 각 결정은 `결정 / 근거 / 대안 / 재검토 조건`으로 적었습니다. 새 결정은 맨 아래에 번호를 이어서 추가합니다.

## 0. 판단의 원칙 (모든 결정에 공통)

| # | 원칙 | 이 프로젝트에서의 의미 |
|---|---|---|
| A | **실제 환경에서의 일반화가 우선** | 같은 출처(같은 태블릿, 같은 대본)에서 얻은 점수는 낙관적으로 본다. 최종 판정은 실제 마이크·실제 장소 녹음으로 한다 |
| B | **문서보다 실측** | 데이터 문서(길이, 샘플레이트, 구간)를 믿지 않고 실제 파일에서 검산한 뒤 설계한다 |
| C | **지름길을 의심하고, 대조 실험으로 확인** | 점수가 너무 쉽게 높으면 모델이 쉬운 단서(말소리 유무, 음량, 패딩 등)를 쓰는지 따로 시험한다 |
| D | **기준값을 0.5로 고정하지 않는다** | 허용할 오경보율(예: 정상 소음의 1%)을 먼저 정하고, 그때의 재현율로 비교한다. 최종 오경보는 후처리까지 포함해 정한다 |
| E | **측정하지 않은 건 추정이라고 쓴다** | 숫자와 해석을 구분한다 (`(추정)`, `(확인 필요)`) |
| F | **자원을 아낀다** | 무료 GPU 한도, 업로드 용량, 시간. GPU가 필요 없는 일은 CPU에서 한다 |
| G | **재현과 중단 복구가 가능해야 한다** | 단계마다 결과를 드라이브에 저장하고, 끝난 실험은 건너뛰며 이어간다 |
| H | **공개 저장소에는 안전한 것만** | 데이터, 모델, 접속 정보, 개인 정보는 올리지 않는다 |

## 결정 목록

### D01. 음성 파트의 목표 범위
- **갱신(11/06)**: 클립은 앱으로 보내지 않고 **파이에만 저장**하기로 팀이 합의했다 (D29).
- **결정**: 위급 음성 감지 + **앞뒤 약 10초 클립을 앱으로 전달**(사람이 확인). 화자 식별은 확장 목표.
- **근거**: 오경보가 완전히 없어질 수는 없으므로, 사람이 소리를 직접 확인하는 구조가 안전하고 현실적이다.
- **대안**: 음성 인식(문장 해석) 기반 키워드 감지.
- **재검토**: 오경보가 후처리로도 허용 범위를 못 맞출 때.

### D02. 마이크 도착 전 작업 방식
- **결정**: 데이터, 모델, 파이 파이프라인, 속도 측정을 마이크 없이 먼저 하고, 파이는 **wav 파일을 마이크처럼 흘려서** 시험한다.
- **근거**: 마이크는 빨라도 11/14 이후. 도착 후에는 검증과 보정에 시간을 쓰는 게 효율적.

### D03. 학습 데이터 선택
- **결정**: AI Hub 위급상황 음성/음향(088)에서 위급 = 도움요청·응급의료·낙상, 정상 = 실내·실외.
- **근거**: 독거노인 집 안의 위급 음성이라는 목적과 직접 관련. 화재·범죄 등은 보류.
- **대안**: 직접 녹음만 사용(양이 부족), 다른 공개 데이터셋.
- **재검토**: 실제 마이크 평가에서 성능이 부족할 때 직접 녹음 비중 확대.

### D04. 다운로드 방식과 범위
- **결정**: 선택 다운로드(필요한 클래스만), Training과 Validation 모두. 큰 파일은 웹 이어받기 도구 사용.
- **근거**: `aihubshell`은 중단 시 받던 파일 삭제, 임시 디스크 2~3배 필요. 코랩 업로드 용량(드라이브 무료 약 15GB)도 고려.

### D05. 오디오 변환 규격
- **결정**: **16kHz 모노**, 헤더의 실제 샘플레이트 기준으로 변환, **4초 창**으로 저장(int16).
- **근거**: 말소리 정보 대부분이 8kHz 이하. 입력이 작아 파이에서 가볍다. JSON의 "44.1kHz"는 신뢰할 수 없음(실측: 44.1/48/96kHz 혼재).
- **대안**: 44.1kHz 유지(저장·계산 3배, 효과 불확실).
- **재검토**: 비언어 소리(쿵, 유리 깨짐)를 다룰 때 고주파가 필요한지.

### D06. 클래스 구성
- **결정**: 낙상 + 도움요청 + 응급의료를 **하나의 "위급 말소리" 클래스**로 합친다 (원래 이름은 메타 파일에 보관).
- **근거**: 알림은 "위급 여부"만 필요. 세부 구분은 사람이 클립을 들으면 된다.
- **재검토**: 앱이 세부 종류를 필요로 할 때.
- **참고**: 낙상 데이터는 쿵 소리가 아니라 "넘어졌어요" 같은 **말소리**가 이벤트 구간. 낙상 충격음 감지는 별도 모델/출력 후보로 보류.

### D07. 짧은 클립 처리
- **결정**: 변환 단계에서는 반복으로 채워 4초를 만들되, **학습에서는 반복 구간을 쓰지 않고 실제 소리 구간에서만 2.5초**를 자른다. 2.5초 미만(약 5%)은 제외.
- **근거**: 무음으로 채우면 "무음 패딩 = 위급"이라는 지름길이 생긴다. 반복으로 채운 창은 청취 시 어색하고 반복 패턴이 새 단서가 될 수 있다.

### D08. 샘플링 규칙
- **결정**: 문구(note)당 최대 40클립, 정상은 소음 종류(note)별로 돌아가며 선택, 위급:정상 창 수 1:1.
- **근거**: 낙상의 47%가 "미끄러졌어요" 한 문구. 균형을 맞춰 한 문구·한 배경에 쏠리지 않게.

### D09. 모델 구조
- **결정**: 로그멜(64 멜 × 251 프레임, 10ms 간격) → 3×3 합성곱 4블록(16-32-64-64) → 전역 평균 → 선형. **6만 파라미터**. 입력 2.5초.
- **근거**: 라즈베리파이에서 실시간으로 돌릴 크기. 이미지 대비 연산량이 매우 작음([04](04_MODEL_EXPERIMENTS.md)).
- **재검토**: 실제 마이크 평가에서 모델 용량이 병목일 때.

### D10. 입력 정규화와 증강
- **결정**: 창마다 로그멜을 평균·표준편차로 표준화, 위급 클립에 정상 소음을 SNR 0~20dB로 얹기(60%), 음량 ±12dB 무작위, SpecAugment.
- **근거**: "위급은 크고 깨끗하다"는 단서(음량, 배경)를 줄이기 위해.
- **한계**: 표준화는 소리가 매우 작을 때 잡음을 키워서 조용한 입력의 오경보를 올림(-40dB에서 9%) → 실제 장비에서는 **소리 크기 게이트**로 보완.

### D11. 평가 원칙
- **결정**: (1) 정상 소음 오경보 1% 기준 재현율, (2) 하위 그룹(클래스, 길이, 음량, 거리, 문구)별 분해, (3) 소음 크기·말소리 길이·위치·음량 탐침, (4) 합성음 시험, (5) 문구·연령 홀드아웃.
- **근거**: 원칙 C와 D. 같은 출처의 평균 점수만으로는 지름길을 알 수 없다.

### D12. 일상 말소리를 정상에 추가 (v1)
- **결정**: Zeroth-Korean(CC BY 4.0) 낭독 음성을 정상으로 추가. 소음을 섞어서(70%) 위급 클립과 환경을 맞춤. 시험 화자는 학습 화자와 분리.
- **근거**: v0가 일반 말소리를 94.5%(기준 0.5) 위급으로 판단. 정상에 말소리가 없던 것이 원인.
- **한계**: 낭독은 실제 대화·TV와 다르고, "읽는 말투 vs 연기 말투"를 배웠을 가능성이 있음.
- **재검토**: 마이크 도착 후 TV·라디오·대화를 직접 녹음해서 추가.

### D13. 모델 선택 시점
- **결정**: v0는 검증 AUC가 가장 높은 에폭(18번째), v1과 실험들은 마지막 에폭을 사용.
- **근거**: 검증 세트로 에폭을 고르면 점수가 약간 낙관적이 된다. 실험 비교에서는 선택 편향을 없애기 위해 마지막 에폭으로 통일.

### D14. 코랩 운영 방식
- **결정**: GPU가 필요 없는 작업(다운로드, 변환, 진단)은 **CPU 런타임**, 학습만 **GPU**. 실험마다 모델과 결과를 드라이브에 즉시 저장하고 끝난 실험은 건너뛰며 이어서 실행. 노트북 A/B/C로 분리.
- **근거**: 무료 GPU 한도는 비공개·변동.
- **유료 플랜**: 지금은 불필요. 마이크 후 막히면 **Pay As You Go 일회 구매**(구독 아님, 유닛 90일 유효)를 검토. 자세한 내용 [06](06_COLAB_RUNBOOK.md).

### D15. 파이 배포 방식
- **결정**: **ONNX + numpy 특징 추출**(PyTorch는 파이에 설치하지 않음), 파이썬 가상환경(venv).
- **근거**: 가볍고 설치가 쉽다. 학습 쪽 PyTorch와의 결과 동일성을 검산(차이 7e-06 / 2e-07).

### D16. 기준값과 후처리
- **결정**: 기준값은 0.5로 두지 않고 **허용 오경보율에서 정한다**. 후처리로 (1) 연속 N회 감지, (2) 소리 크기 게이트, (3) 알림 후 쉬는 시간을 둔다. 값은 실제 마이크 데이터로 정한다.
- **근거**: 판단을 초당 한 번 한다면 하루 86,400번이라, 오경보율 1%도 하루 약 860번. 후처리 없이는 쓸 수 없다.

### D17. 저장소 공개 규칙
- **결정**: 데이터, 학습된 모델, 키, IP, 계정, 와이파이 이름, 팀원 개인 정보는 올리지 않는다 (`.gitignore`, `<PLACEHOLDER>`).
- **근거**: 저장소가 공개 상태이고, AI Hub 데이터는 재배포가 제한된다.

### D18. 평가는 연속(스트리밍) 조건의 시간당 오경보와 이벤트 감지율로 (2026-11-03)
- **결정**: 모델과 규칙의 비교 기준을 "창 단위 재현율"에서 **연속 스트림에서의 시간당 오경보 + 위급 이벤트 감지율 + 감지 지연**으로 바꾼다.
- **근거**: 창 단위 재현율 0.93이 연속 환경에서는 오경보 목표를 지킬 때 0.26이었다(원칙 A, D).
- **재검토**: 마이크 후 실제 녹음으로 스트림을 만들 수 있을 때.

### D19. 오경보 허용 수준은 팀이 정한다 (2026-11-03)
- **결정**: 합의 전까지는 임시 목표(소음 시간당 1회 이하, 말소리 3회 이하)로 비교한다. 실제 목표(하루 몇 회)는 팀 합의 후 확정.
- **근거**: 시간당 1회도 하루 24회라서, 하루 5회 이하를 원하면 지금 모델로는 불가능하다.

### D20. 긴 코드는 파일로 전송한다 (2026-11-03)
- **결정**: 파이 터미널에 긴 스크립트를 붙여 넣지 않고, 파일로 받아 `scp`로 보낸다.
- **근거**: 붙여 넣기에서 코드 중간이 사라졌다(코랩에서도 약 10,300자에서 잘린 적이 있음).

### D21. v2 학습 방법 (2026-11-04)
- **결정**: 조용한 소리까지 학습(-10~20dB), 소리 조각 삽입, v1이 틀린 샘플 채굴(오답 25%, 놓친 문장 30%), 40에폭, 체크포인트 매 에폭.
- **근거**: 스트리밍 평가에서 오경보 목표를 지키면 감지율이 0.26이었고, 먼 소리(-12, -18dB)가 특히 약했음.
- **재검토**: 공통 요소 중 어느 것이 효과인지는 따로 빼 본 실험이 없다. 필요하면 에폭, SNR 범위만 바꿔 비교.

### D22. 파이 후보 모델 (2026-11-04)
- **결정**: 주 후보 `v2_wide`(엄격 감지율 0.48, 파이4에서 54.7ms), 대체 `v2_no_part`(0.45, 23.1ms). 두 모델의 차이는 시험 오차 안.
- **근거**: 둘 다 실시간의 11% 이하로 돌아가고, 최종 장비 파이5는 더 빠르다.
- **재검토**: 실제 마이크 데이터가 생기면 두 모델을 다시 비교해서 최종 결정.

### D23. 마이크 도착 전까지 모델 개발 중단 (2026-11-04)
- **갱신(11/07)**: 이 결정은 직접 녹음한 시험 세트로 평가를 시작하면서 바뀌었다 (D25~D28).
- **결정**: 합성 스트림 기준으로 모델을 더 올리지 않고, 실제 마이크 데이터로 개선한다.
- **근거**: 합성 스트림에서 고른 규칙과 기준값은 낙관적이고 마이크가 바뀌면 달라진다. 남은 개선 여지는 실제 데이터에 있다.

### D24. ONNX 스레드는 1개로 고정 (2026-11-04)
- **결정**: `threads=1`(설정으로 변경 가능).
- **근거**: 기본값(4스레드)에서 판단 한 번 42ms, 1스레드는 23ms. 특징 추출(numpy)과 번갈아 실행하는 구조에서는 스레드를 늘려도 이득이 없다.

### D25. 위급 감지는 단어 인식 방식으로, 소리 분류 모델은 단독 알림에 쓰지 않는다 (2026-11-08)
- **결정**: 말소리를 글자로 바꿔 위급 단어를 찾는 방식(Whisper + 규칙)을 주 경로로 한다. 소리 분류 모델(CNN, YAMNet+MLP)은 단독 알림에 쓰지 않고, 영상과 겹칠 때만 의미를 갖는 보조 신호로 남긴다(현재 음성은 `distress`·`impact`를 보내지 않음).
- **근거**: 학습에 쓰지 않은 기기의 3시간 일상 소리에서 소리 모델은 재현율 85%일 때 오경보 시간당 92회, 오경보 시간당 3회 이하에서는 재현율 9%였다. 단어 방식은 같은 3시간과 다른 녹음 87분에서 오경보 0회, "도와주세요" 34/34, 새 문장 31/39 ([11](11_VOICE_ASR_TRACK.md)).
- **대안**: 소리 모델 개선(곡선을 따라가면 재현율이 같이 떨어져 불가), 영상과의 결합만으로 보완.
- **재검토 조건**: 어르신 목소리, TV 속 대사, 마이크·먼 거리에서 단어 방식이 크게 무너질 때.

### D26. 파이4 음성 인식 구성 (2026-11-08)
- **결정**: Whisper tiny(int8, 탐색 폭 5), 소리 크기 -28dBFS 이상 구간만 처리, 위급 단어 규칙(단어 경계 + 완성된 표현, "불러주세요"와 문장 끝 "살려" 포함), 첫 인식에 비슷한 조각이 있고 단어는 없을 때만 small로 한 번 더 인식(단어를 미리 알려 주지 않음), 스레드 2.
- **근거**: 응급 e1·e2 17/17, 새 문장 31/39, 오경보 0, 구간당 평균 2.7초, 3시간 중 6.1% ([11 §6~7](11_VOICE_ASR_TRACK.md)). small을 주 모델로 쓰면 구간당 18.8초라 반복 호출에서 처리가 밀린다.
- **대안**: base 상시(79%, 5.5초), small 상시(90%, 18.8초).
- **재검토 조건**: 파이5와 영상 동시 실행 시험 후 모델 크기와 재시도 조건(재시도 조건을 넓히면 재현율은 오르지만 지연이 늘어남), reSpeaker에서 게이트 기준 보정.

### D27. 인식 설정은 반드시 오경보 시험과 함께 확정한다 (2026-11-08)
- **결정**: 재현율을 올리는 설정은 응급 녹음 결과만 보고 확정하지 않고, 학습에 쓰지 않은 연속 일상 소리(3시간)와 다른 녹음의 오경보를 같이 본다.
- **근거**: 미리 알려 준 단어는 응급 재현율을 17/17로 올렸지만 3시간에서 같은 단어를 48번 만들어 냈다. 하이브리드도 다른 녹음에서 3회 ([09 #22](09_CORRECTIONS_AND_LESSONS.md)).

### D28. 최종 시험은 학습에 쓰지 않은 기기·시간으로 (2026-11-08, D18 보강)
- **결정**: 학습에 쓴 소리에서의 오경보는 참고만 하고, 최종 판단은 다른 기기로 녹음한 3시간 연속 소리(C)로 한다. C는 학습에도 설정 선택에도 쓰지 않는다.
- **근거**: 학습에 쓴 시험용 녹음에서 시간당 1.5회였던 모델이 C에서는 19회였다 (약 13배).

### D29. 통신 구조와 클립 (2026-11-06~07, 팀 합의)
- **결정**: 파이 로컬 MQTT(파이 → 폰 단방향), 음성 `home/alert/audio`·영상 `home/alert/vision` → 통합 판단 프로그램(앱 파트) → `home/alert/fusion`·`home/status`. 클립은 앱으로 보내지 않고 파이에만 저장. 오경보 피드백 버튼은 없고 통합 판단 프로그램의 기록 파일로 대체.
- **근거**: 앱 파트 의견(안드로이드 백그라운드 제한, 파이는 상시 켜져 있음, 가족이 같은 집이라 직접 확인). 상세는 [12](12_TEAM_AGREEMENT_V05.md), [08 §7](08_TEAM_SHARING.md).

### D30. 알림 정책 (2026-11-07, 일부는 제안)
- **합의**: 음성만 또는 영상만 잡히면 "주의", 영상 + 음성이 10초 안에 겹치면 "긴급", 음성 `help_request`가 30초 안에 2회 이상이면 "긴급", 같은 사고는 앱에서 기존 알림을 업데이트(등급이 오르면 다시 울림).
- **제안(미합의)**: 음성 `distress`·`impact` 단독은 "기록만", `lying_long` 단독은 "긴급"(앱 파트 찬성, 이미지 파트의 "오래" 기준 대기).
- **재검토 조건**: 마이크 도착 후 실측(TV처럼 같은 말이 반복되는 소리의 긴급 오경보).

### D31. 외부 음성 인식 대신 직접 설계한 작은 모델 (2026-11-11, 11/16 확정)
- **결정**: 도움 요청 말(A 도와주세요, B 살려·구해주세요, C 사람 살려, D 119)만 잡는 TC-ResNet을 직접 설계·학습한다. Whisper는 최종 시스템(2단계 확인 포함)에 쓰지 않고 비교 숫자(65/73)로만 남긴다.
- **근거**: 연구회 취지(직접 공부·개발). Whisper 3시간 연속은 쿨러 없이 83.7°C로 속도 제한, 자체 모델은 판단 16ms·1시간 60.3°C.
- **대안**: 2단계(자체 모델 후보 → Whisper 확인) — 오경보는 줄지만 취지와 맞지 않아 제외.
- **재검토 조건**: 최종 시험에서 재현이 Whisper와 크게 차이 날 때.

### D32. 학습용과 시험용 녹음 분리, 다른 사람 목소리는 시험 전용 (2026-11-16)
- **결정**: Pi 녹음 중 R(위급 말)·TN(오답)은 학습, P·N은 시험, C는 기준·게이트 조정에만 쓴다. 다른 사람 목소리(S2~)는 학습에 넣지 않는다.
- **근거**: 섞으면 시험 점수가 부풀려짐(D18·D28과 같은 원칙). 처음 듣는 목소리로 시험할 조건을 남김.
- **재검토 조건**: 다른 사람 목소리에서 재현이 크게 떨어질 때(그때는 새 학습용 녹음을 따로 만듦).

### D33. 게이트를 고정값 대신 바닥 소리 기준으로 (2026-11-16)
- **결정**: 최근 1.5초 안에 "바닥 + 15dB" 이상이고 -65dBFS 이상인 구간이 있을 때만 모델을 돌린다(예전 서비스 -43dBFS 폐기).
- **근거**: 같은 1m에서도 말 최대 크기 중앙값이 -38~-46dBFS로 날마다 달라 -43dBFS는 평소 목소리의 17~65%만 통과시켰다.

### D34. 알림 기준 0.95 (2026-11-16, 11/18 유지)
- **결정**: 3번 평균 점수가 0.95 이상인 상태가 2번 연속이면 알림.
- **근거**: 개발용 실제 녹음에서 오경보 0을 지키는 가장 낮은 값(47/73). Pi 약 21시간 오경보 3번(시간당 0.14번).
- **재검토 조건**: 4차 모델, 최종 시험(11/23).

### D35. 정확도보다 안정화·연동 우선 (2026-11-16)
- **결정**: 남은 기간은 미세한 정확도 향상보다 온도·안정화·MQTT 연동·문서화를 우선하고, 성능은 학습용 오답 추가 정도로만 올린다.
- **근거**: 시스템 품질은 영상·앱과 함께 결정되며, 음성만 높이는 이득이 작음.

### D36. MQTT 브리지 방식, 클립은 clip_url, occurred_at은 말 시작 (2026-11-16~17, 앱 팀 제안 수용, D29 일부 대체)
- **결정**: 음성 파이가 MQTT 중앙 서버(계정 audio·fusion·app·bridge·watchdog, 권한 acl)이고, 영상 알림은 브리지로 넘어온다. 클립은 파이 클립 서버(`:8080/clips/`) 주소를 JSON `clip_url`에 담는다. `occurred_at`과 `incident_id`는 말 시작 시각, 같은 초면 `_2`.
- **근거**: 앱이 한 서버만 관리. 앱은 영상·음성이 10초 안에 함께 나면 긴급으로 판단해 실제 소리 난 시각이 필요.
- **대안**: 앱이 두 서버에 각자 접속(시험 통과) — 앱 관리가 복잡해 제외.
- **재검토 조건**: 음성 파이가 꺼지면 영상 알림도 끊기는 문제가 점검에서 문제될 때.

### D37. 현장 운영: 자동 실행, 와이파이 절전 끄기, IP 고정, 시험 키트 (2026-11-18)
- **결정**: 서비스는 systemd로 자동 실행(멈추면 5초 뒤 재시작), 와이파이 절전 끄기, 공유기에서 IP 고정. 다른 파이에서의 점검은 시험 키트 zip(설치·마이크 없는 시험 모드)으로 한다.
- **근거**: 15시간 녹음 중 와이파이 절전으로 연결이 끊김. 1차 점검에 본인이 없어도 MQTT·브리지·앱 호환을 시험해야 함.

### D38. 통신 기준을 김우석 MQTT 배포 문서 v1.1.0으로 (2026-11-23, D36의 브리지 부분 대체)
- **결정**: 브로커는 음성 파이(R1) 하나. 영상 파이와 확인 화면은 R1에 직접 접속(브리지 없음). 계정 audio·vision·app 3개와 문서의 ACL을 쓴다. 기기 상태는 `home/status/audio`·`vision`에 online/offline 문자열(retain), 비정상 종료는 브로커가 LWT로 offline. JSON 4필드·`clip_url`·`occurred_at`(말 시작)·`_2` 규칙은 D36 그대로.
- **근거**: 11/20 1차 점검에서 브리지 토픽 전달이 오류의 원인이었다. 직접 접속은 구성이 단순하고, 상태 토픽으로 각 파이가 살아 있는지 화면에서 바로 보인다.
- **대안**: 브리지 유지 — 오류 지점이 남아 제외.
- **재검토 조건**: R1이 꺼지면 영상도 끊기는 점(단일 브로커)이 시연에서 문제가 될 때.

### D39. 음성 서비스는 상태·LWT만 추가하고 통신 모듈로 바꾸지 않는다 (2026-11-23)
- **결정**: `kws_service.py`의 기존 발송 부분에 LWT 등록, 접속 시 online, 정상 종료 시 offline만 넣는다. 토픽·값·retain·QoS는 문서와 같다.
- **근거**: 기존 발송은 실패한 알림을 파일에 쌓아 10초마다 다시 보낸다. 배포 모듈은 연결이 끊기면 발행을 실패로 끝내므로, 바꾸면 오히려 알림을 잃을 수 있다. 감지 로직을 건드리지 않아 검증한 결과(P25~P27)가 그대로 유효하다.
- **대안**: 배포 모듈(`mqtt_module.py`)로 교체 — 재전송 기능을 다시 만들어야 해서 제외.
- **재검토 조건**: 팀이 모든 파이에 같은 모듈 사용을 요구할 때.

### D40. 현장 네트워크는 휴대폰 핫스팟, R1 주소는 자동 찾기 (2026-11-23)
- **결정**: 시연은 본인 휴대폰 핫스팟에 모든 기기를 붙인다. R1 주소는 고정하지 않고, 확인 화면이 같은 네트워크(/24)에서 1883 포트가 열린 기기를 찾아 접속한다. 영상 파이에는 그때 찾은 주소를 알려 준다. 클립 주소는 음성 서비스가 보낼 때마다 IP를 다시 확인한다.
- **근거**: 핫스팟은 켤 때마다 대역이 바뀔 수 있다(리허설 `10.221.81.x`). 이름 접속(`.local`)은 핫스팟에서 믿을 수 없었다(집에서도 공유기 덕이었음). 자동 찾기는 리허설에서 약 2초 안에 R1을 찾았다.
- **대안**: 이름(`r1-audio.local`) 접속 — 실패. 고정 IP — 핫스팟 대역이 바뀌어 불가.
- **재검토 조건**: 같은 네트워크에 1883 포트를 연 기기가 둘 이상일 때(화면에 후보 목록이 나오고 `--host`로 지정).

### D41. 결과 확인 화면을 음성 팀이 노트북 웹으로 만든다 (2026-11-23)
- **결정**: 11/23 회의에서 결과 확인 화면을 음성 팀이 맡기로 했다. 노트북 웹(`dashboard/`, Flask)으로 만들고 `app` 계정으로 구독만 한다. 확인됨·오경보 표시는 노트북에만 저장한다. 긴급/주의 같은 판단 등급은 만들지 않고, 10초 연결선은 표시용 참고다.
- **근거**: 감지 결과를 눈으로 확인하고 시연·보고서 근거(실측 정밀도, 발생→도착 시간, 규약 준수, 연결 기록)를 남기기 위해. 앱 설치형은 백그라운드 알림만으로 며칠이 걸려 일정에 맞지 않는다. 통신 규약을 하나도 바꾸지 않는다.
- **대안**: 안드로이드 앱 — 일정상 제외. Streamlit — 실시간 갱신·화면 구성 자유도가 낮아 제외.
- **재검토 조건**: 휴대폰 푸시 알림이 꼭 필요해질 때.
